# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a dotfiles repository for macOS/Linux. Dotfiles are symlinked into `$HOME` via the install script. The repo uses a whitelist-based `.gitignore` — everything is ignored by default, and tracked files are explicitly un-ignored.

## Key Commands

- **Install dotfiles:** `.bin/install.sh` — backs up existing dotfiles to `~/.dotbackup/`, then symlinks tracked entries into `$HOME`.
- **Uninstall dotfiles:** `.bin/uninstall.sh` — removes only the symlinks that point into this repo and restores any matching `~/.dotbackup/` backup. Both scripts accept `--dry-run` (`-n`) and `--debug` (`-d`).
- **Preview without changes:** `.bin/install.sh --dry-run` (`-n`) — prints every action without touching the filesystem.
- **Install with debug:** `.bin/install.sh --debug` (`-d`) — runs with `set -x` tracing.
- **Install dependencies:** `brew bundle --file=./Brewfile` — installs the CLI toolchain (`Brewfile` is curated; VSCode/Go/local packages are intentionally excluded).
- **Full bootstrap (clean install):** `.bin/bootstrap.sh` — installs oh-my-zsh, the dependency toolchain, and runs `install.sh`. Uses `brew bundle` when Homebrew is present; on a **Linux host without Homebrew** (e.g. the shared GPU server) it installs the `flake.nix` toolchain with `nix profile` instead (see the Nix bullet under Architecture). A host with neither Homebrew nor Nix aborts with install instructions. Flags: `--skip-browser`, `--force`, `--no-brew` (use Nix even where Homebrew exists; Linux only).
- **Update the Linux toolchain:** `nix flake update` (bumps `flake.lock`), commit, then re-run `bootstrap.sh` on the host — a re-run takes the `nix profile upgrade` path.
- **Apply macOS system defaults:** `.bin/macos-defaults.sh` — keyboard/Finder/screenshot settings. Opt-in (not run by install.sh), macOS-only, supports `--dry-run`/`--debug`.
- **CI:** GitHub Actions (`.github/workflows/check.yml`) runs four jobs: `ubuntu` (install/uninstall smoke tests incl. dry-run no-op and idempotency), `nix` (builds `flake.nix` for x86_64-linux, checks every tool starts, runs `bootstrap.sh --no-brew` twice to cover both the add and the upgrade path), `lint` (`shellcheck` on all `.bin/*.sh`), and `secrets` (gitleaks scan).

## Architecture

- **`.gitignore` uses a whitelist pattern:** The top of `.gitignore` ignores everything (`/*`, `/.**`), then specific files/directories are un-ignored with `!` prefixes. When adding new dotfiles, you must add a corresponding `!` entry in `.gitignore`.
- **Shell:** oh-my-zsh (git plugin) with its theme disabled (`ZSH_THEME=""`); the prompt is provided by **starship**, initialized last in `.zshrc`. Modern CLI tools (zoxide, fzf, eza, bat) are wired up in `.zshrc`, each guarded by `command -v` so a missing tool never breaks shell startup. `.zshrc` also defines an **`rm` guard**: it refuses any target that is not a regenerable artifact (`node_modules`, `__pycache__`, `.DS_Store`, …) or under `/tmp`, `$TMPDIR`, or a `.cache/` path, and points at `trash` instead; `command rm` is the deliberate escape hatch. Note that startup is dominated by oh-my-zsh's `compinit` (the `zoxide`/`starship`/`direnv`/`uv`/`fzf` `eval`s together cost ~30ms of a ~250ms startup), so caching those `eval`s — a common suggestion — is not worth the invalidation bug it introduces.
- **Install mechanism:** `.bin/install.sh` iterates over the repo's `.*` entries and symlinks each into `$HOME`, skipping `.git`, `.claude` (managed via `.config/claude/`), and the repo's own metadata — `.gitattributes`, `.gitignore`, `.github` — which describe *this repository*, not the home directory. All linking goes through the `link_file` helper: an existing symlink at the destination is removed, an existing real file/dir is moved to `~/.dotbackup/` under a slash-flattened name (so e.g. `.claude/settings.json` and `.gemini/settings.json` never collide), then the symlink is created.
- **Uninstall mirrors install:** `.bin/uninstall.sh` walks essentially the same destinations as `install.sh`, in reverse — the one deliberate divergence is its skip list (below). Its `unlink_file` helper removes a destination **only if** it is a symlink whose target is inside this repo (`readlink` prefix check), then restores the matching `~/.dotbackup/` backup if one exists — so foreign symlinks and real files are never touched. Its skip list is deliberately **not** identical to `install.sh`'s: only `.gitattributes` is excluded there. `.gitignore` and `.github` *were* linked by earlier versions, so uninstall keeps walking them in order to clean up the symlinks already sitting in `$HOME`; excluding them too would strand those links permanently.
- **`settings.json` formatting drift is absorbed by a git clean filter:** Claude Code rewrites `.config/claude/settings.json` with different key ordering and formatting whenever it saves, producing diffs indistinguishable from real edits (see `604f68b`, where a moved `statusLine` block and an inlined-to-multiline array accounted for the whole change). `.gitattributes` declares `filter=jsonsort`, `.gitconfig`'s `[filter "jsonsort"]` points at `.bin/git-jsonsort.sh`, and that script normalises **only** object keys (`jq -S`) plus the `permissions` `allow`/`deny`/`ask` arrays. Every other array keeps its order deliberately — `hooks` is execution-ordered, and `autoMode.environment` is prose whose line order carries meaning. The working tree may be reordered freely; only the index is pinned to the canonical form. The script exits **non-zero** when `mktemp` or reading stdin fails: a clean filter that exits 0 hands its output straight to the index, so swallowing those errors would stage an empty or truncated file with no warning. It passes input through unchanged only when `jq` is absent, or when the file was read in full and is genuinely invalid JSON.
- **`.gitconfig` degrades gracefully without `delta`, but not without `~/.gitmessage`:** `core.pager` and `interactive.diffFilter` both go through `.bin/git-delta.sh`, which execs `delta` when it is on `PATH` and otherwise falls back to `less` (pager) or `cat` (diff filter). Both install paths now ship `delta` (Homebrew via the `Brewfile`, Linux via `flake.nix`), so the fallback only matters on a host where neither has run yet. The one remaining hard dependency is `commit.template = ~/.gitmessage`, which needs the symlink `install.sh` creates: with the template missing, interactive `git commit` aborts (`exit 128`, `fatal: could not read ...`). `git commit -m` is unaffected, since `-m` bypasses the template entirely.
- **On Linux, Nix supplies the tools — it does not manage the dotfiles:** `flake.nix` exposes one `buildEnv`, `packages.<system>.dotfiles-cli`, holding the tools these dotfiles themselves reference (`rtk`, `agent-browser`, `herdr`, `delta`, `gh`, `jq`, the linters, the shell tools); `flake.lock` pins nixpkgs to `nixos-unstable`, which only advances once Hydra has built it, so hosts pull signed binaries from `cache.nixos.org` instead of compiling. Three deliberate limits: **no home-manager** (Claude Code and Codex write their own config files back, which home-manager's read-only `/nix/store` links would break — linking stays with `install.sh`); **macOS stays on Homebrew** (casks, npm and uv packages would remain outside Nix anyway, so it would add a system rather than replace one); **no `tmux`** (a shared host keeps a long-lived tmux server, and a client of a different version fails with `protocol version mismatch`). The attribute is named rather than `default` because `nix profile` derives an element's name from the flake's *directory* when the attribute is `default`; the fixed name `dotfiles-cli` is what lets `bootstrap.sh` find it and choose `upgrade` over `add`, since re-adding an existing element is a silent no-op. `.zshenv` sources Nix's profile script (as it does `brew shellenv`) so non-interactive shells see the tools too.
- **`.config/` is linked per-app, at file granularity:** rather than symlinking `~/.config/<app>` as a whole (which would swallow app-managed session data), the installer links individual files: `.config/claude/*` → `~/.claude/`, `.config/{codex,gemini}/*` → `~/.{codex,gemini}/`, and `.config/herdr/*` → `~/.config/herdr/` (herdr is the one XDG-style consumer, so its destination stays under `~/.config/`). The `skills/` subdirectories of claude and codex are linked directory-by-directory into `~/.claude/skills/` and `~/.codex/skills/`. This means `.config/claude/CLAUDE.md` and `.config/claude/RTK.md` are the user's **global** agent instructions (linked to `~/.claude/`), distinct from this repo's root `CLAUDE.md`, which documents the repo itself.
- **Host-specific overrides live under `.config/claude/hosts/<hostname>/`:** after linking the shared `.config/claude/*` files, `install.sh` links any files in a `hosts/<hostname>/` directory matching the current host (`$HOSTNAME`, falling back to `uname -n`) into `~/.claude/`, **overriding** same-named shared files. This keeps machine-specific instructions off other machines — e.g. `hosts/p-team-17/CLAUDE.md` carries the shared GPU server's usage notes and overrides the shared `@RTK.md` stub, while its `@RTK.md` import still resolves to the shared `~/.claude/RTK.md`. Other hosts (macOS etc.) have no matching directory, so nothing is linked.
- **Path-scoped rules live in `.config/claude/rules/`:** `install.sh` links each `.md` there into `~/.claude/rules/`, Claude Code's **user-level** rules directory, so they apply in every project on the machine — never put repo-specific rules here, they belong in that repo's own `.claude/rules/`. A rule whose frontmatter carries a `paths:` glob loads only when Claude reads a matching file; a rule **without** `paths:` loads at launch and costs context in every session, exactly like CLAUDE.md. That is the whole reason to use rules rather than growing CLAUDE.md, so keep every rule here path-scoped. The current two gate the same linters this repo's CI runs: `shell-scripts.md` (shellcheck) and `github-actions.md` (actionlint).
- **Review vocabulary is shared between humans and AI reviewers:** `.github/PULL_REQUEST_TEMPLATE.md` carries the `[must]` / `[imo]` / `[nits]` / `[ask]` / `[fyi]` prefix convention in an HTML comment, where review bots pick it up. It maps onto the `code-review` skill's own output: 必須 = `[must]`, 推奨 = `[imo]` or `[nits]`.
- **Claude and Codex skills are intentionally separate, not duplicates:** `.config/claude/skills/` and `.config/codex/skills/` hold same-named skills (`code-review`, `address-review`, …) whose contents deliberately differ per tool — Claude skills carry `aliases:`/`allowed-tools:` frontmatter (Claude Code format), while Codex skills omit those and use a prose form Codex understands. Do **not** try to reconcile them into a single shared source; edit each tool's copy independently.
- **Third-party skills are reproduced at install time, not vendored — with one exception:** skills that are pristine copies of public upstreams are *not* committed here (a committed copy silently goes stale). `agent-browser` ships inside its npm package (`Brewfile`), so `install.sh` symlinks `~/.claude/skills/agent-browser` straight to the package's bundled copy, which tracks the installed version automatically. On a Linux host without npm, the nixpkgs `agent-browser` package bundles the same skill, and `install.sh` falls back to linking `~/.nix-profile/skills/agent-browser` — through the profile symlink rather than the resolved `/nix/store` path, so a `nix profile upgrade` carries the link along. The exception is `skill-creator` (Anthropic official, Apache-2.0): it has no package distribution, so a pinned copy is vendored under `.config/claude/skills/skill-creator/` with `SOURCE.md` recording the upstream commit — update it by re-copying, not by editing in place.
