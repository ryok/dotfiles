# Address Review

レビューコメントを確認し、妥当な指摘だけを実装に反映する。レビュアーの指摘はそのまま採用せず、技術的妥当性とプロジェクト文脈を評価する。

## 入力の解釈

- 引数なし: 直前の会話に含まれるレビュー内容を対象とする
- 数値のみ: PR 番号として解釈し、`gh api` でコメントを取得する
- `github.com` を含む URL: GitHub PR URL として解釈し、PR 番号を抽出して `gh api` でコメントを取得する
- それ以外: レビュー内容が書かれたファイルパスとして扱う

## 取得コマンド

PR 番号がある場合は以下を使う。

```bash
gh api repos/{owner}/{repo}/pulls/{number}/reviews
gh api repos/{owner}/{repo}/pulls/{number}/comments
```

## 実行フロー

1. レビューコメントを取得または読み込む
2. 各コメントの妥当性を評価する
3. 妥当な指摘のみ修正する
4. 修正しない指摘は理由を明示する
5. 最後にレビュー対応サマリーを出す

## 判断基準

- 技術的に正しいか
- プロジェクトの方針や既存設計と整合するか
- 実装上のトレードオフとして受け入れるべきか
- 対応によって別の不具合や退行を招かないか

## 出力フォーマット

```markdown
## レビュー対応サマリー

### 指摘一覧
- [ ] 指摘1の概要
- [ ] 指摘2の概要

### 対応した指摘
| 指摘 | 修正内容 |
|------|----------|
| 指摘1 | 修正の概要 |

### 対応しなかった指摘
| 指摘 | 理由 |
|------|------|
| 指摘X | 理由 |
```

## 注意事項

- 指摘を鵜呑みにしない
- 対応しない場合はレビュアーが理解できる理由を書く
- 修正後に関連テストや差分確認を行う
- GitHub API や push が必要な場合は Codex の承認フローに従う
